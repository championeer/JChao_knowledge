客服系统是每个企业都绕不开的东西。不管你是电商、物流、金融还是 SaaS，只要用户数上来，客服就是刚需。

![Image](https://pbs.twimg.com/media/HIGbcgsaUAAxos4?format=jpg&name=large)

但一个尴尬的现实是：大多数企业做的所谓「智能客服」，上线第一天就被用户测出原形。用户问「我的订单什么时候到」，机器人回「您的订单已签收」，实际上物流还在中转站。

你说它是人工智障吧，它确实接了大模型。你说它是客服 Agent 吧，它其实就只是个更聪明的 FAQ。

问题出在哪？不是大模型不行，是大部分企业把客服 Agent 理解成了**接大模型 + 写个 prompt（提示词） + 套个聊天框**。上线后发现该有的问题一个不少：幻觉（模型瞎编信息）、越权、流程混乱、出了事查不到原因。

那企业级客服 Agent 到底该怎么做？OpenAI 最近开源了一个客服 demo（openai-cs-agents-demo），场景是航空公司客服。我花了一个下午把代码拆了一遍，发现它最值得看的不是聊天框，也不是 prompt 技巧。**它是一个企业级客服 Agent 的最小完整样板：多 Agent 分工、业务工具调用、上下文状态管理、独立安全检查、可观测前端，五样东西一个不少。**

这篇文章把它拆开，我们一起看看企业客服 Agent 到底该怎么做。

## 这个 Demo 里有什么

先看结构。整个仓库分两块：

后端是 Python + FastAPI + OpenAI Agents SDK，核心代码在 airline/ 目录下：

- [agents.py](https://agents.py/) — 6 个 Agent 的定义、提示词、工具绑定和移交关系
- [tools.py](https://tools.py/) — 11 个模拟业务工具，查航班、改签、改座、补偿等
- [guardrails.py](https://guardrails.py/) — 两个安全检查（安全护栏），相关性校验和越狱检测
- [context.py](https://context.py/) — 会话上下文状态管理
- demo\_data.py — mock（模拟）的航班行程、备选航班和补偿数据

前端是 Next.js + ChatKit React，左右分屏。右边是客户看到的聊天界面，左边是Agent 视角，能看到当前哪个 Agent 在干活、调了什么工具、上下文怎么变的、安全检查过了没。

这个结构本身就说明了很多问题。一个企业客服 Agent 不是聊天框 + 大模型就完事了，它需要五个层：**路由层（Agent 分工）、执行层（工具调用）、状态层（上下文管理）、保护层（Guardrails）、观察层（可观测性）**。

接下来的每个部分，我就围绕这五个层展开。

![Image](https://pbs.twimg.com/media/HIGbgw4bwAEs-la?format=jpg&name=large)

## 多 Agent 不是炫技，是把企业真实的部门拆出来

这个 demo 里定义了 6 个 Agent：

**Triage Agent** — 入口路由。判断用户想干什么，交给对应专员。对应企业里的客服入口 / 一线分诊。

**Flight Information Agent** — 查航班状态、判断转机风险、找备选航班。对应订单查询 / 物流状态查询部门。

**Booking & Cancellation Agent** — 预订、改签、取消。对应订单变更 / 退订团队。这个 Agent 还能调用 book\_new\_flight 和 cancel\_flight，在 demo 里这两把钥匙只给了它。

**Seat & Special Services Agent** — 改座位、处理医疗或特殊座位需求。对应个性化服务 / 特殊需求支持。它握着 update\_seat 和 assign\_special\_service\_seat。

**FAQ Agent** — 回答行李政策、Wi-Fi、补偿政策等问题。对应企业知识库 / 政策咨询。它只有一个工具：faq\_lookup\_tool，被明确要求：不要用模型知识回答。

**Refunds & Compensation Agent** — 创建补偿 case，发酒店券、餐券、交通补贴。对应售后 / 赔付 / 权益团队。只有它能调用 issue\_compensation。

看出门道了吗？

每个 Agent 不是一个抽象角色，而是把企业里真实存在的部门、职责和权限拆成了代码。Booking Agent 能改签但不能发补偿，Refunds Agent 能发补偿但不能改签，FAQ Agent 能查政策但不能改订单。

对比一下大多数企业现在的做法：写一个万能客服的 prompt，把所有业务规则塞进去，然后祈祷模型不要越权、不要搞混流程、不要给不该给的信息。这个做法在小规模试用时还行，一旦上了生产流量，问题会密集出现。

为什么呢？因为 prompt 是软约束，tool 权限是硬约束。你写一句**不要越权操作**，模型可能遵守，也可能不遵守。但如果你根本没把改签工具发给 FAQ Agent，它想越权都没途径。

所以这个 demo 给出的第一个关键设计原则是：**多 Agent 不是架构上的花活，它是把企业真实的职责边界、权限边界和流程边界，用代码固定下来。**

![Image](https://pbs.twimg.com/media/HIGbtD3aEAIskbi?format=jpg&name=large)

## Handoff 是受控的业务流程，不是无限跳转

有了多个 Agent，下一个问题就是：它们之间怎么交接？

demo 里的做法是显式定义 handoff 关系。Triage Agent 可以交接给五个专员中的任何一个，专员之间也可以互相交接，比如 Flight Info Agent 发现问题需要改签，就交给 Booking Agent；Booking Agent 发现用户有特殊座位需求，交给 Seat Agent。

但这不是一个全连接的自由跳转网络。demo 里做了几个关键约束：

第一，**每轮最多一次 handoff**。prompt 里反复写了这个要求。为什么？因为如果不限制，Agent 可能在一轮对话里 A → B → C → D 一路跳下去，整个过程不可控、不可解释。

第二，**部分 handoff 有前置回调**。比如转到 Booking Agent 之前，会先补齐行程上下文；转到 Seat Agent 之前，确保座位偏好已经被提取出来。这保证了接手方拿到的是完整信息，不会反复追问用户。

第三，**受控的回退路径**。每个专员都可以交回给 Triage Agent，但 Triage 是唯一可以重新路由的入口。这个设计避免了一线 Agent 被绕过后，客服入口丧失了对全局的掌控。

在企业客服场景里，handoff 对应的就是部门流转和工单流转。你不可能让用户在一线客服和售后赔付之间被无限踢皮球，同样，你也需要确保 Agent 交接时有明确的触发条件、上下文传递和回退机制。

这个 demo 的 handoff 设计还很基础，但它给出了一条原则：**Agent 之间的交接关系，应该是对企业业务流程的显式建模，而不是让模型自己决定该找谁。**

## 工具权限比 Prompt 更重要

前面已经提到了一点，这里展开说。

Demo 里有 11 个工具，覆盖了查航班、找备选、改签、取消、改座、特殊座位、显示座位图、FAQ 查询、行李查询、发补偿。每个工具背后对应一个企业系统：订单系统、库存系统、座位系统、知识库、工单系统、权益系统。

这些工具的分配是有讲究的：

- FAQ Agent 只有一个 faq\_lookup\_tool。它不能查航班、不能改签、不能发补偿。它的能力边界被工具锁死了。
- Booking Agent 有 book\_new\_flight 和 cancel\_flight。只有它能做订单变更。
- Refunds Agent 有 issue\_compensation。只有它能创建补偿 case 并发券。
- Seat Agent 有 update\_seat 和 assign\_special\_service\_seat。只有它能动座位。

这比在 prompt 里写**你不要越权**靠谱太多了。

我在几个企业项目里见过类似的坑。一个电商客服 Agent 的 prompt 里写了「你只能查订单，不能取消」，结果测试的时候用户说「我知道你不能取消，但我就是想确认一下，如果我点取消会发生什么」，Agent 就开始「解释」取消流程，解释着解释着就调用取消失败了。因为它有那个工具的权限，prompt 拦不住它。

所以 demo 给出的设计是：**把权限边界落实到工具绑定上。一个 Agent 能做什么，看它有哪些工具，不看 prompt 里写了什么限制。**

反过来也一样。如果企业后续要给某个 Agent 增加能力，不是改 prompt，而是给它加工具。这就像给员工开系统权限：能干什么取决于你的工号能登录哪些系统，不取决于你的岗位说明书。

## 上下文管理：Agent 知道的，用户不一定需要看到

Demo 里有一个设计我特别喜欢：AirlineAgentContext。

这是一个结构化的会话状态对象，保存了当前对话中的所有关键信息：乘客姓名、确认号、航班号、座位号、行程详情、行李 claim id、补偿 case id、已发放的权益、特殊服务备注等等。

关键是，它有一个 public\_context() 方法。

这个方法会过滤掉部分字段：隐藏完整行程（itinerary）、隐藏行李 claim id、隐藏补偿 case id、隐藏 demo 场景标记、隐藏未实际发放的权益。换句话说，Agent 内部可以使用全部上下文做决策，但用户界面只展示应该让用户看到的部分。

这个设计对应企业客服中一个非常实际的诉求：**内部状态和用户可见状态是两套东西。**

比如，一个补偿 case 的创建逻辑里可能有系统判定的赔付上限、风控标记、内部备注，这些信息 Agent 需要知道才能做正确决策，但绝不能直接展示给用户。再比如，用户的完整订单链路可能包含多个状态变更记录，Agent 决策时需要全量信息，但用户只需要看到当前状态和下一步。

很多企业做客服 Agent 时忽视了这一点。上下文一股脑全塞给前端，用户能看到内部工单号、系统策略名、甚至风控评分。这不仅是体验问题，也是安全隐患。

Demo 的做法很简单但有效：**用结构化状态 + 公开/内部字段分离，做到 Agent 全知全能，用户只看该看的。**

## Guardrail 应该是独立安全检查层

Demo 里有两个 input guardrail（输入安全检查，在用户消息到达业务 Agent 之前先过一遍）：

**Relevance Guardrail（相关性检查）**：用 gpt-4.1-mini 判断用户消息是否和航空客服相关。用户如果问**帮我写段代码**，直接拦截。

**Jailbreak Guardrail（越狱攻击检测）**：同样是 gpt-4.1-mini，判断用户是否在尝试绕过系统指令、索要 prompt（提示词）或进行攻击。

两个 guardrail 都用的轻量模型，主业务 Agent 用的是 gpt-5.2。这是一个成本和延迟上的折中：安全检查不需要最强模型，但需要高频执行。

更有意思的设计是：guardrail 只检查最新一条用户消息，不是整个对话历史。这样做更快，也能减少误伤。但它对跨轮上下文攻击、渐进式指令注入的防御力有限，demo 里没有解决这个问题。

不过这个 demo 的 guardrail 最重要的启示不是技术实现，而是架构原则：安全检查不应该是主 Agent prompt 里的一句**请遵守安全规范**，而应该是一个独立的、可替换的、在主 Agent 之前执行的安全层。

这个独立层的意义在于：

- 安全检查失败了，可以直接拦截，不消耗主模型的 token（大模型的调用按 token 计费，省 token 就是省钱）。
- 安全策略更新不需要改主 Agent 的 prompt，改了 prompt 还得重新测试业务表现。
- 可以并行部署多个专用 guardrail，每个只检查一个维度。

但这个 demo 的 guardrail 离生产还很远。真实企业客服至少还需要：

- **身份校验**：这通对话请求的用户是谁？有没有登录？
- **权限校验**：这个用户有权做这个操作吗？这条订单是这个用户的吗？
- **PII 脱敏（个人敏感信息脱敏）**：对话记录和日志中不能出现身份证号、手机号、银行卡号等敏感信息。
- **高风险操作二次确认**：退款、取消、改签这类操作，需要明确确认，不能一句话就执行。
- **人工接管条件**：Agent 连续三轮无解、用户情绪明确激动、涉及投诉和赔付争议，应该自动转人工。
- **审计日志**：谁在什么时候做了什么，哪条 guardrail 放行或拦截了，必须可追溯。
- **工具调用结果校验**：guardrail 不只检查用户输入，也应该检查工具返回的数据是否合法、完整。

简单说：**demo 的 guardrail 是概念验证，生产级 guardrail 需要覆盖输入、输出、工具调用和人工接管整条链路。**

## 可观测性不是锦上添花，是上线前提

这个 demo 的前端最特别的地方：它不是只有一个聊天框。

右边是客户视角，普通的 ChatKit 聊天界面，用户只看到正常的客服对话。

左边是 Agent 视角，一个面板叫 Agent View，里面展示：

- 当前哪个 Agent 在活跃
- 所有可用的 Agent 列表
- 会话上下文（筛选后的公开版本）
- Guardrails 状态（通过/拦截）
- Runner Output（运行日志）：一个按时间线排列的事件流，包括 handoff（Agent 移交）、tool\_call（调了什么工具，参数是什么）、tool\_output（工具返回了什么）、context\_update（上下文哪些字段变了）、message（Agent 说了什么）

这个东西的价值，做过客服系统的人一看就懂。

Agent 上线之后，你最常被问到的问题不是它的回复准不准，而是：它为什么把钱退了？它为什么把订单取消了？它为什么把用户转到了投诉部门？它查到的订单信息是对的吗？

如果你只有聊天记录，这些问题一半答不上来。因为用户只看到了 Agent 的最终回复，看不到中间过程。

但如果你有 Runner Output，你就能回溯完整的执行链路：用户问了什么 → Triage 路由到哪个 Agent → 调用了哪个工具 → 工具返回了什么数据 → 数据触发了什么上下文更新 → Agent 基于这些数据做了什么决策。

这不再是猜它为什么这么回答，而是还原它每一步做了什么。

把这个能力放进企业客服系统，它至少支撑三个场景：

**故障排查**：用户投诉 Agent 做错了事，客服主管打开 Agent View，看工具调用记录，发现问题不是 Agent 错了，是订单系统返回了过期数据。问题定位从几小时缩到几分钟。

**质量监控**：质检团队不再只看对话文本，而是看完整的执行链路。Agent 有没有跳过必要步骤？有没有调用不该调的工具？handoff 决策对不对？

**线上优化**：产品团队看高频被拦截的问题、频繁失败的 tool call、经常回退的 handoff，针对性优化 prompt 和流程。

可惜的是，现在大多数企业的客服 Agent 项目，预算和时间都花在了**让聊天更自然**上，可观测性被当成了**后续再说**。结果就是 Agent 上线后，出了问题没人知道原因，团队开始互相甩锅，最后老板说**AI 不靠谱，先停了吧**。

其实不是 AI 不靠谱，是上线之前没装后视镜。

## 一个案例走完所有设计

说了一堆设计原则，用一个 demo 里的完整流程把它们串起来。

场景：用户 Morgan Lee 从巴黎经纽约飞奥斯汀，第一段航班 PA441 因为天气延误了 5 小时。

用户输入：**I'm flying Paris to Austin via New York and my first leg is delayed.**

然后发生的事情：

**第一步，路由。** Triage Agent 收到消息，识别为航班异常问题。它调用 get\_trip\_details，从 mock 数据中匹配到 Morgan Lee 的行程（确认号 IR-D204），写入上下文。然后 handoff 到 Flight Information Agent。

这里有三个设计点在起作用：Triage Agent 的路由判断、工具调用填充上下文、handoff 传递完整信息。

**第二步，诊断。** Flight Information Agent 调用 flight\_status\_tool，发现 PA441 因天气延误 5 小时，预计 19:55 起飞。系统计算后发现，这会错过在纽约的转机航班 NY802。

这里体现的是：Agent 不只是回答状态，而是在执行业务判断：它需要知道延误会导致错过转机。

**第三步，找方案。** Flight Information Agent 调用 get\_matching\_flights，找到两个备选航班：NY950（第二天 9:45，座位 2A）和 NY982（第二天 13:20，座位 3C）。

注意这里有一个细节：两个备选航班的座位信息已经有了。这就为后续自动改签和选座铺好了路。

**第四步，执行。** Flight Information Agent 把结果 handoff 给 Booking & Cancellation Agent。Booking Agent 直接调用 book\_new\_flight，改签到 NY950，座位 2A。

这一步是关键：用户没有说帮我改签，Agent 主动做了。因为上下文里已经有了所有需要的信息（确认号、当前航班、备选航班），Agent 不需要再问一遍「要帮你改吗」。

这个设计的来源是 prompt 里一句指令：「数据齐全时自动串联工具，不要每一步都停下来问用户」。

**第五步，特殊需求。** 用户提到有医疗原因，需要前排座位。Booking Agent 把这个需求 handoff 给 Seat & Special Services Agent。Seat Agent 调用 assign\_special\_service\_seat，分配了 1A。

这里有一个隐式的上下文传递：改签后的航班信息已经在上下文里了，Seat Agent 不需要再查一遍。

**第六步，补偿。** 用户抱怨过夜延误。Seat Agent handoff 到 Refunds & Compensation Agent。Refunds Agent 调用 faq\_lookup\_tool 查了补偿政策，然后调用 issue\_compensation，创建补偿 case，发放酒店券（最高 180 美元）、餐券（60 美元）、地面交通补贴（40 美元）。

注意：Refunds Agent 只调了 FAQ 工具查政策，它没有 FAQ Agent 那么受限，它可以查政策和发补偿两件事都做，但改签和改座绝不碰。

整个流程走下来，用户看到的是：一个客服全程帮他解决了延误、改签、选座、补偿。而 Agent 内部经历了 4 次 handoff（Triage → Flight Info → Booking → Seat → Refunds），调用了 6 个工具（查行程、查状态、找备选、改签、特殊座位、查政策 + 发补偿），上下文被更新了多次，每个操作都有工具权限约束。

**这哪是在回答问题，这明明是在多个业务系统之间跑流程。**

## 生产落地还差什么

拆完之后，必须说一句：这个 demo 明确标注了是演示用途，不是生产系统。客观指出它的不足，比一味吹捧更有价值。

**1\. 真实系统集成。** Demo 里所有业务数据都是 mock 的。生产环境需要对接 CRM（客户管理系统）、订单系统、工单系统、支付系统、库存系统、用户身份系统、权益系统。每一个对接都是真实工程量的来源。

**2\. 持久化。** 当前用 in-memory store（内存存储，服务重启后数据全丢）。生产需要数据库、会话存储和完整的审计日志。

**3\. 权限体系。** Demo 没有用户认证，没有区分用户、客服、管理员、系统角色。真实客服系统里，用户看到的数据、Agent 能做的操作、管理员能看的日志，是三层不同的权限。

**4\. 高风险操作确认。** 取消订单、退款、修改个人信息这类操作，demo 里 Agent 可以直接执行。生产中需要二次确认、额度限制和审批流。

**5\. 人工接管。** Demo 里没有人类客服接管的机制。真实客服系统必须设计转人工的条件：连续 N 轮无解、情绪识别、投诉关键词、高价值用户、赔付争议。

**6\. 错误处理。** 真实系统会遇到 API 超时、返回异常数据、库存变化、支付失败、并发冲突。Demo 里工具都是同步 mock，不存在这些问题。生产需要重试、回滚、幂等设计。

**7\. 评估体系。** 怎么知道这个 Agent 做得好不好？只看对话记录不够。需要建立一套指标：问题解决率、转人工率、误操作率、平均处理时长、客户满意度、赔付成本。而且要区分 Agent 的问题和业务系统的问题。

**8\. 行李 Agent 缺失。** 代码里有 baggage\_tool，prompt 里多次提到 Baggage Agent，但实际没有定义和接入独立行李 Agent。说明这个 demo 自己也没做完。

所以如果要用这套样板做企业客服 Agent，补齐顺序应该是：先接真实数据源（让 Agent 有用），再做持久化和审计（让系统可靠），然后上权限和确认机制（让系统安全），最后建评估体系（让系统可度量）。

## 最后

回过头来看这个 demo，它展示的不是一个客服聊天机器人，而是一个 Agent 操作系统的雏形。

**路由层**（Triage + Handoff）决定这件事交给谁办 **执行层**（Tool calling）决定能办到什么程度 **状态层**（Context）保证办事过程中不丢失信息 **保护层**（Guardrails）防止不该办的事被办了 **观察层**（Agent View + Runner Output）确保出了事能查到为什么。

这五层里，大多数企业现在只关注了聊天体验那一小块。

真正难的不是接入大模型。ChatGPT 的 API 调通只要五分钟。真正的难点是把企业内部系统封装成安全、可控、可审计的工具，让 Agent 既能把事办了，又不会办出事。

OpenAI 这个 demo 给了一个可参考的起点。它不完美，但它至少说清楚了一件事：**企业客服 Agent 不是更聪明的 FAQ，而是一套能被自然语言驱动的业务流程系统。**

下一步，就看谁先把这五层落进生产了。
